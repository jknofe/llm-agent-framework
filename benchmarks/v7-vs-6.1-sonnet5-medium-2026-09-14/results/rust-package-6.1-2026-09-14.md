## Observations

1. **v6.1's opt-in `/spec`+`/build` gating worked cleanly for an
   autonomous run**: since the orchestrator explicitly named `/spec`
   and `/build` in the task steps, the "never start one on your own"
   guard in `AGENTS.md`/the skill files didn't block anything - it
   only matters for spontaneous invocation, and an explicit STEP
   3/STEP 4 in the prompt is exactly the invited case.
2. **The `reviewer` sub-agent type from `.claude/agents/reviewer.md`
   was not spawnable from this session** (only `claude`,
   `claude-code-guide`, `Explore`, `general-purpose`, `Plan`,
   `statusline-setup` were available as `subagent_type` values here).
   The build skill's documented fallback ("spawn a fresh
   general-purpose sub-agent given only the diff and the criteria")
   worked exactly as written: I pasted `reviewer.md`'s own checklist
   into the general-purpose agent's prompt and it followed it
   faithfully, cross-reading `Makefile`/`build.rs` and catching nothing
   wrong. The skill's fallback ladder is well-designed for a harness
   where the named sub-agent type isn't wired up.
3. **The task's own framing ("the `build-release` dependency runs the
   `ci-release` feature first, generating `completions/` and `man/`")
   was already true of the unmodified Makefile** - `build-release` ->
   `target/release/satty` already carries `--features ci-release`. No
   Makefile change was needed there; the only real gap was the missing
   `deb` target and the missing `[package.metadata.deb]` table. Good
   example of a task statement that's partly "confirm," not "change."
4. **cargo-deb's asset-rename semantics (trailing slash = keep source
   name, no trailing slash = literal target filename) mattered for
   exactly one entry**: `completions/satty.bash` has to map to
   `.../completions/satty` (no `.bash`), matching the Makefile's own
   `install -Dm644 completions/satty.bash $(BASHDIR)/satty` rename.
   Missing that would have silently shipped a wrongly-named bash
   completion; the gate's `dpkg-deb --contents` check catches this
   class of bug directly, which is a stronger check than "does
   `cargo deb` exit 0."
5. **No local `cargo`/GTK toolchain existed in the dev sandbox this
   session ran in** (only the packaging container had `cargo-deb`+
   `dpkg-deb`), so `cargo fmt --check` / `cargo clippy` / `cargo test`
   / `cargo metadata` could not be independently re-executed as the
   spec's own acceptance criterion asked for - that criterion was
   satisfied by static reasoning (diff scoped to two additive,
   non-Rust-source edits) plus the sub-agent review, not by running the
   commands. Recorded explicitly as a residual gap in `.ai/notes.md`
   rather than silently marked done.
