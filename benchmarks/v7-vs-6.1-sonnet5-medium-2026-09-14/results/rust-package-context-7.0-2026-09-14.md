## Observations

1. **Makefile `install` target as spec was unambiguous.** It fully
   enumerates 11 shipped paths (binary + desktop + icon + license + 6
   completions + man), so translating it into a cargo-deb `assets` array
   was a direct 1:1 mapping with no design judgment calls - low-ambiguity
   task. The two non-obvious traps both live in the `install` recipe
   itself, not anywhere the framework could pre-digest: the bash
   completion source `completions/satty.bash` installs under the
   destination filename `satty` (no extension), and the zsh completion
   keeps its source's leading-underscore filename `_satty` at the
   destination. Missing either would produce a working-looking deb with a
   silently wrong completion path.
2. **build.rs's `ci-release` feature gate was the one fact that made the
   Makefile target actually functional**, and it required reading
   `build.rs` directly rather than any framework doc: `completions/` and
   `man/` are gitignored and only materialize on disk when that feature is
   active, which is exactly why `deb: build-release` (not `deb: build`)
   is correct - `build-release` compiles with `--features ci-release`.
   Context-only arm gets no shortcut here; this has to be discovered by
   reading the build script.
3. **AGENTS.md's generated project-context section arrived empty**
   (one line, "Populated by /explore. Do not edit by hand."), so the
   `/explore`-equivalent pass had to be done from scratch this run:
   `probe.py`, then reading Makefile/Cargo.toml/build.rs by hand to fill
   in build/test/lint commands and note that no human was available to
   confirm them. This cost several tool calls that a context arm with a
   pre-populated map would skip - the framework's explore skill worked as
   designed but front-loaded work onto this session rather than a prior
   one.
4. **No local Rust/GTK toolchain in the agent's shell** (`cargo`, `rustc`
   not on PATH) meant AGENTS.md protocol item 2 ("tests and lint must
   pass... the whole suite") could not be honored literally. Since the
   task only touched packaging metadata (Cargo.toml `[package.metadata.
   deb]`, one new Makefile target) and no Rust source, the practical
   fallback was: TOML-syntax validation (`python3 tomllib`), a `make -n
   deb` dry run, and the prescribed docker-based `cargo deb` gate as the
   real functional check. The framework's protocol doesn't have an
   explicit fallback for "the project's own toolchain is absent from this
   environment"; an autonomous run has to substitute the best available
   verification and say so, which is what `.ai/notes.md` records as
   assumption 2.
5. **`.ai/notes.md` append-and-commit discipline was frictionless** for
   this single-file, mechanical change: one commit covered both the
   explore-context fill-in and the task's numbered assumptions/decisions,
   no `/spec`/`/build` machinery invoked (correctly - the task explicitly
   forbade it and the change is small, self-contained, and low-risk).
