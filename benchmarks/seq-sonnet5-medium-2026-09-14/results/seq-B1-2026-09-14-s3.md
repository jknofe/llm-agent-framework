## Observations

1. The working tree already had unrelated, uncommitted work implementing a `rename-column` command/method (CLI, db.py, docs, tests) plus what looks like a seeded one-line bug in `Table.is_fts`'s LIKE pattern (`content="{}"` changed to `content=[{}]`, which no longer matches real FTS5 `content=` schema text). Per task instructions this pre-existing uncommitted state was left untouched and not fixed; the new `drop-column` work was added on top of it without disturbing it.
2. Regenerating `docs/cli-reference.rst` with `cog` (as the project's own tooling would) produced large unrelated diffs because the sandbox's installed `tabulate` version supports fewer table formats than the version used to originally generate that file, polluting ~80 lines of `--fmt` help text across unrelated commands. Rather than ship that dependency-version noise, the cog run was discarded and the new reference section was hand-inserted in cog's exact output format, keeping the diff scoped to the actual feature.
3. `drop_column` was implemented as a thin `ALTER TABLE ... DROP COLUMN ...` call (mirroring `rename_column`'s and `add_column`'s directness) rather than routing through the existing `transform(drop=...)` table-rebuild path used internally by `convert()`; SQLite validates the column exists before executing the ALTER, so an invalid column name raises `AlterError` and leaves the table byte-for-byte unchanged, satisfying the task's "must raise and leave the table unchanged" requirement without needing a rebuild-and-rollback strategy.
