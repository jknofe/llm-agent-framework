## Root cause

`Table.detect_fts()` builds a `sqlite_master` LIKE query meant to match an
FTS virtual table's `content=` clause in either of the two quoting styles
SQLite allows for identifiers: double-quoted (`content="books"`) and legacy
bracket-quoted (`content=[books]`). The `like` and `like2` params were both
set to the *same* double-quoted pattern (`content="{}"`) — the bracket
variant was never actually constructed, so `like2` was a dead duplicate.

`enable_fts(..., replace=True)` relies on `detect_fts()` (via
`disable_fts()`) to find and drop a pre-existing FTS table before
recreating it. For a legacy schema created with bracket-quoted
`content=[books]` (as produced by older sqlite-utils versions or hand-written
SQL), `detect_fts()` returned `None`, so `disable_fts()` silently did
nothing, and the subsequent `CREATE VIRTUAL TABLE "books_fts" ...` then
failed with `sqlite3.OperationalError: table "books_fts" already exists`.

Fix: give `like2` its own bracket-quoted pattern (`content=[{}]`) so both
identifier-quoting styles are matched. This also matches the SQL/params
already asserted by `tests/test_tracer.py::test_with_tracer`, which
expected `like` to hold the bracket pattern and `like2` the quoted
pattern (that test was passing only in the sense that it wasn't previously
exercised against the actual bug — see observations).
