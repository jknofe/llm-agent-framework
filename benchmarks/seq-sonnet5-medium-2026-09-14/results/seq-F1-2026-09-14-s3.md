## Goal
sqlite-utils has `add-column`/`add_column()` and `rename-column`/`rename_column()`
for altering a single column, but no way to drop one column without going
through the heavier `transform(drop=...)` table-rebuild path. Add a
`Table.drop_column(name)` method (using native `ALTER TABLE ... DROP COLUMN`,
same no-version-guard style as `add_column`'s `ADD COLUMN` and
`rename_column`'s `RENAME COLUMN`) and a mirroring `drop-column` CLI command.
Dropping a column that does not exist must raise and leave the table
unchanged, matching `rename_column`'s missing-source-column behavior.

## Notes
- Assumption 1: SQLite's native `ALTER TABLE ... DROP COLUMN` (available
  since SQLite 3.35.0, 2021) is used directly, with no version guard,
  matching the existing style of `add_column` (`ADD COLUMN`) and
  `rename_column` (`RENAME COLUMN`), neither of which guards on SQLite
  version either. This is consistent with the codebase's existing
  ecosystem-support stance rather than a new policy decision.
- Assumption 2: error-handling mirrors `rename_column` exactly (raise
  `NoTable` if table missing, checked first; let SQLite's own
  `OperationalError` surface unswallowed for a missing column - SQLite
  itself already leaves the table unchanged when `ALTER TABLE ... DROP
  COLUMN` fails on an unknown column, so no pre-check like `add_column`'s fk
  validation is needed for that case).
- Assumption 3: `--ignore` on the CLI command suppresses both "table does
  not exist" and "column does not exist" errors, mirroring `rename-column`'s
  `--ignore` (which covers both "column does not exist" and "new name
  already in use").
