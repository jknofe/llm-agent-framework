## Observations

1. `Table.rename_column` mirrors `Database.rename_table`'s minimal style: no
   pre-flight schema parsing, just `ALTER TABLE ... RENAME COLUMN ... TO ...`,
   which SQLite has supported natively since 3.25.0. The three guard checks
   (table exists, source column exists, target name free) run before any SQL
   executes, so an error path never touches the table - this directly satisfies
   the "leave the table unchanged" requirement without needing a transaction.
2. `AlterError` (not `sqlite3.OperationalError`, which `rename_table` lets
   propagate untouched) was chosen deliberately: `rename_table` has no
   pre-checks and just lets SQLite's own `OperationalError` surface, whereas
   `add_column`/`add_foreign_key` in this same file already validate and raise
   `AlterError` for user-facing "this precondition failed" cases. Renaming onto
   a duplicate name is exactly that kind of validated precondition, so
   `AlterError` was the more consistent choice, and the CLI command's
   `except AlterError` handler follows the same pattern as `add-column`'s CLI
   command elsewhere in `cli.py`.
3. `docs/cli-reference.rst` is cog-generated from live `--help` output.
   Running `cog -r` in this sandbox produced a much larger diff than intended
   because the sandbox's `tabulate` package (installed via apt, v0.8.10) is
   older than whatever generated the currently-committed file, so `--fmt`'s
   list of table formats differs. Regenerating for real would have silently
   reverted unrelated help text for a dozen other commands. Caught this by
   inspecting `git diff --stat` before finalizing, discarded the full cog
   run, and hand-inserted only the new `rename-column` entry with content
   verified against an actual `CliRunner` invocation - an example of why an
   auto-generated doc's diff needs eyeballing even when a "just run cog"
   canonical regen path exists.
