## Goal
`sqlite-utils` has a `rename-table` CLI command and `Database.rename_table()`
API method but no equivalent for renaming a single column. Add a
`rename-column` CLI command and a `Table.rename_column(old, new)` API method
that mirror the existing rename-table pattern, using SQLite's native
`ALTER TABLE ... RENAME COLUMN ... TO ...` (supported since SQLite 3.25.0,
well below any version this project targets - `add_column` already relies on
`ALTER TABLE ... ADD COLUMN` unconditionally). Renaming a column onto a name
that already exists on the table must raise and must not modify the table.

## Acceptance criteria
- [x] `Table.rename_column(old, new)` exists in `sqlite_utils/db.py`, renames
      the column via `ALTER TABLE ... RENAME COLUMN`, and returns the `Table`
      instance (matching the `Table.duplicate()` return-self convention).
- [x] Calling it on a table that does not exist raises `NoTable`.
- [x] Calling it with `new` equal to an existing column name on the table
      raises `AlterError` *before* executing any SQL, and the table's schema
      and data are unchanged (verified by a test that checks `columns_dict`

## Notes
- Assumption 1 (no human available): use native
  `ALTER TABLE t RENAME COLUMN old TO new` rather than routing through
  `Table.transform(rename={...})`. `transform()` rebuilds the whole table
  (copies all rows, rewrites indexes/triggers/FKs) which is far heavier than
  what `rename-table`'s `ALTER TABLE ... RENAME TO` does, and the task says
  to mirror the `rename-table` pattern, which is a direct, cheap `ALTER
  TABLE`. `add_column()` already uses unconditional `ALTER TABLE ... ADD
  COLUMN` with no SQLite-version guard, so no version guard is added here
  either.
- Assumption 2: raise `AlterError` (not `InvalidColumns`) for the
  new-name-collision case. `AlterError` is already used elsewhere in
  `add_column()` for alter-time precondition failures ("table does not
  exist" / "has no column"); `InvalidColumns` is used for
  column-does-not-exist validation in `transform_sql`, which is the inverse
  problem, not the collision problem.
- Assumption 3: `NoTable` is raised (not left to SQLite) when the table
  itself does not exist, matching `Table.duplicate()`'s explicit
  `self.exists()` check, since `Table.rename_column` is a `Table` method
  (unlike `Database.rename_table`, which lets sqlite3 surface "no such
  table").
- Assumption 4: CLI `--ignore` on `rename-column` suppresses both
  "table/column does not exist" and "new name already exists" failures,
  matching `rename-table --ignore`'s stated scope ("ignore any errors caused
  by the table not existing, or the new name already being in use").
