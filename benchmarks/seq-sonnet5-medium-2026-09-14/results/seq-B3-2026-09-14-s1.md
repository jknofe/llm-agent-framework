## Root cause

`Table.detect_fts()` builds a SQL `LIKE` query with two patterns, `like` and
`like2`, meant to catch the two ways SQLite can quote an FTS5 table's
`content=` clause in its stored schema: double-quoted (`content="books"`,
current `enable_fts()` output) and legacy bracket-quoted
(`content=[books]`, produced by older sqlite-utils versions or hand-written
schemas). Both `like` and `like2` had been set to the identical
double-quoted pattern, so `detect_fts()` could never recognize a
bracket-quoted legacy FTS table. This regressed a fix from commit `1a28416`
("Fix for detect_fts failing on [], refs #694"), which had originally set
`like` to the bracket-quoted pattern; a later change (`49b1d39`, "seed:
benchmark bug state") reverted `like` back to duplicate `like2`.

The test creates a table with a legacy bracket-quoted `content=[books]` FTS5
table, then calls `enable_fts(..., replace=True)`. `enable_fts()` correctly
decides the FTS table needs recreating (its schema string doesn't match the
freshly generated one) and calls `disable_fts()`, which calls
`detect_fts()` to find the existing FTS table to drop. Because `detect_fts()`
could not match the bracket-quoted schema, it returned `None`, so
`disable_fts()` dropped nothing, and the subsequent `CREATE VIRTUAL TABLE
books_fts ...` failed with `sqlite3.OperationalError: table "books_fts"
already exists`.

## Fix

Restored the `like` pattern in `Table.detect_fts()` (sqlite_utils/db.py) to
match the legacy bracket-quoted form (`content=[{name}]`), while `like2`
keeps matching the double-quoted form. This lets `detect_fts()` recognize
both legacy and current FTS table schemas, so `disable_fts()` can correctly
find and drop the old FTS table before `enable_fts(replace=True)` recreates
it.

## Observations

1. The bug was a single-line regression: a duplicate/near-duplicate `LIKE`
   pattern silently reintroduced an issue (#694) that had already been fixed
   upstream in commit `1a28416`; `git log -p` on the affected lines was
   the fastest way to find the intended fix and confirm the seeded bug
   commit (`49b1d39`, "seed: benchmark bug state") was the direct cause.
2. The two `LIKE` clauses (`like` / `like2`) in `detect_fts()` have no
   distinguishing names or comments explaining that they cover two distinct
   quoting styles (double-quote vs. bracket-quote); a short inline comment
   would have made the duplication bug obvious on read, without needing
   history archaeology.
3. Test suite is comprehensive here: `tests/test_fts.py` alone has a
   dedicated regression test for the bracket-quoting case, and the fix was
   verified both narrowly (`pytest tests/test_fts.py`, 47 passed) and against
   the full suite (`pytest`, 1080 passed / 16 skipped / 0 failed), giving
   high confidence the one-line fix has no side effects elsewhere.
