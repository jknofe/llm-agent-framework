## Root cause

`Table.detect_fts()` builds a SQL query with two `LIKE` patterns (`like` and
`like2`) meant to match an FTS content table declared either with
double-quoted identifiers (`content="books"`, the modern form `enable_fts`
itself generates) or legacy bracket-quoted identifiers (`content=[books]`,
as produced by older sqlite-utils versions / hand-written schemas). In the
seeded state both `like` and `like2` were identical
(`content="{}"`-style), so the bracket-quoted legacy form was never matched.

In the failing test, a legacy `books_fts` table is created directly with
`content=[books]`. Calling `enable_fts(..., replace=True)` computes
`should_recreate = True` (schema text differs from the freshly generated
CREATE statement), so it calls `disable_fts()`, which calls `detect_fts()`
to find the existing FTS table to drop. Because `detect_fts()` couldn't
match the bracket-quoted form, it returned `None`, `disable_fts()` dropped
nothing, and the subsequent `CREATE VIRTUAL TABLE books_fts ...` failed with
`sqlite3.OperationalError: table "books_fts" already exists`.

The fix restores the bracket-quoted pattern for `like` (this exact fix
previously existed upstream in commit `1a28416` — "Fix for detect_fts
failing on [], refs #694" — and had been reverted in the seed commit
`82ce715`), so `detect_fts()` again recognizes both legacy bracket-quoted
and modern double-quoted `content=` table references.

## Observations

1. The bug was a straight reversion of a known upstream fix (commit
   `1a28416`, "Fix for detect_fts failing on [], refs #694"): the seed
   commit `82ce715` duplicated the `like2` (double-quote) pattern into
   `like`, silently dropping the bracket-quoted match. `git log -p` on the
   `detect_fts` line range immediately surfaced the original fix, making
   root-causing fast once the traceback pointed at `detect_fts`'s failure
   to find the legacy table.
2. The failure mode is a classic "silent no-op then downstream crash":
   `detect_fts()` fails closed (returns `None` on no match) rather than
   raising, so `disable_fts()` quietly does nothing and the real error only
   surfaces two calls later as an unrelated-looking `OperationalError:
   table "books_fts" already exists` from `executescript`. The stack trace
   alone underspecifies the root cause; understanding `enable_fts`'s
   replace/should_recreate logic was necessary to trace it back to
   `detect_fts`.
3. The fix is a single-line, one-character-class change (bracket quoting
   vs double quoting) with no behavioral ambiguity — both patterns coexist
   as alternate matches for old vs. new schema text, so restoring `like`
   cannot regress the `like2` (double-quote) path. Full-suite run (1080
   passed) confirms no collateral effects.
