## Goal
Add a way to remove a single column from an existing table, mirroring the
existing `add-column` command / `Table.add_column()` pattern: a
`Table.drop_column(name)` Python API method and a `sqlite-utils
drop-column` CLI command built on top of it. Dropping a column that does
not exist on the table must raise and leave the table unchanged (no
partial drop).

## Notes
- Assumption 1: use SQLite's native `ALTER TABLE t DROP COLUMN c`
  directly (available since SQLite 3.35.0, 2021) rather than routing
  through `Table.transform(drop=[...])` (a full table-rebuild that also
  exists in this codebase). The task explicitly asks for a dedicated
  `Table.drop_column(name)` mirroring `add_column`'s single-purpose,
  direct-ALTER style, and the prior `rename-column` change (same
  session line, same codebase) made the identical call for `RENAME
  COLUMN`, finding no SQLite-version gating elsewhere in db.py for
  newer ALTER TABLE features. `transform(drop=[...])` remains available
  for callers who need the rebuild (e.g. to also drop a column that is
  part of an index or a generated-column dependency SQLite's native
  DROP COLUMN refuses); not superseding it here.
- Assumption 2: existence checks (`self.exists()` for the table,
  `name in self.columns_dict` for the column) are done in Python before
  running SQL, matching `rename_column`'s pattern and giving a clean
  `NoTable`/`AlterError` rather than a raw `sqlite3.OperationalError`.
  Both checks happen before any `ALTER TABLE` executes, so a failure
  leaves the table byte-for-byte unchanged (no `ALTER TABLE ... DROP
  COLUMN` is issued at all in the error paths).
- Assumption 3: return value is `self` (Table), following
  `add_column`/`rename_column`'s chaining convention.
- Assumption 4: CLI `--ignore` suppresses both "column does not exist"
  and "table does not exist", matching `rename-column`'s `--ignore`
  scope (that command's `--ignore` covers old-column-missing and
  table-missing; drop-column has no third failure mode analogous to
  rename's "new name collides").
- Reused from `.ai/notes.md` (rename-column session, same repo):
  `cog -r` on the full `docs/cli-reference.rst` introduces unrelated
  `--fmt` diff noise from this sandbox's `tabulate` version - hand-insert
  the new section instead, captured via `CliRunner().invoke(cli.cli,
  ["drop-column", "--help"])`. Also reused: `Table.columns`/
  `columns_dict` return `[]`/`{}` silently for a nonexistent table, so
  check `self.exists()` first rather than inferring a missing table from
  an empty `columns_dict`.
- Review gate: the `reviewer` sub-agent type is not registered in this
  harness's agent list (only `claude`, `claude-code-guide`, `Explore`,
  `general-purpose`, `Plan`, `statusline-setup`), so per the build
  skill's fallback a fresh `general-purpose` sub-agent was spawned
  instead, given only the diff (scoped to the drop-column hunks, with
  an explicit note to ignore two unrelated pre-existing uncommitted
  changes already in the working tree - `rename_column` and an FTS
  `like2` fix from earlier sessions), the acceptance criteria, and the
  reviewer's brief text. It found the stated criteria fully met, plus
  one real gap outside the explicit criteria: the CLI command only
  caught `NoTable`/`AlterError`, so a column SQLite itself refuses to
  drop (part of the primary key, `UNIQUE`, indexed, etc - confirmed
  empirically raises a raw `sqlite3.OperationalError`) would surface as
  an unhandled traceback instead of a clean `click.ClickException`.
  Fixed: added an `except OperationalError` handler to the CLI command
  (mirrors `add-column`'s CLI handling of the same exception type,
  respects `--ignore`), added a Python-API test
  (`fresh_db["t2"].drop_column("id")` on a pk column, asserting
  `sqlite3.OperationalError` and the table left unchanged) and a CLI
  test (drop of the `id` primary-key column, with and without
  `--ignore`) documenting the new behavior in `docs/python-api.rst`.
