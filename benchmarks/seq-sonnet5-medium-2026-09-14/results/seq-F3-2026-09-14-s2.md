## Goal
Add a way to rename a single column on an existing table, mirroring the
existing `rename-table` command / `Database.rename_table()` pattern:
a `Table.rename_column(old, new)` Python API method and a
`sqlite-utils rename-column` CLI command built on top of it. Renaming a
column onto an already-existing column name must raise and leave the
table unchanged (no partial rename, no data loss).

## Acceptance criteria
- [x] `Table.rename_column(old_name, new_name)` exists in
      `sqlite_utils/db.py`, renames the column via
      `ALTER TABLE ... RENAME COLUMN ... TO ...`, and returns `self`
      (mirrors `add_column`'s `return self`, unlike `rename_table` which
      returns `None` - `Table` methods generally chain).
- [x] Raises `AlterError` if `old_name` is not a column on the table
      (checked before executing SQL, so no partial state).
- [x] Raises `AlterError` if `new_name` already exists as a column on the
      table (checked before executing SQL - table is left unchanged).
- [x] Raises `NoTable` if the table itself does not exist (revised from
      "propagates `sqlite3.OperationalError`" - see Notes; mirrors
      `Table.duplicate()`'s explicit `self.exists()` check rather than
      letting a bare SQLite error surface, and the CLI turns it into a
      clean `Table "..." does not exist` message like `duplicate`'s CLI
      command does).
- [x] `sqlite-utils rename-column PATH TABLE COLUMN NEW_NAME` CLI command
      exists in `sqlite_utils/cli.py`, calls
      `db[table].rename_column(column, new_name)`.
- [x] CLI command has an `--ignore` flag: when set, a `does not exist`
      style error (column missing, or table missing) is suppressed
      (exit code 0, no output) instead of raising - mirrors
      `rename-table`'s `--ignore`. A rename onto an existing column name
      still raises even with `--ignore` (that's a name-collision error,
      not a "does not exist" error - `--ignore`'s documented purpose is
      "If column does not exist, do nothing").
- [x] Without `--ignore`, CLI errors exit non-zero with a
      `click.ClickException` message in the style of `rename-table`'s
      (`Table "..." could not be renamed. <detail>`).

## Notes
- Assumption 1: SQLite's native `ALTER TABLE t RENAME COLUMN a TO b`
  (available since SQLite 3.25.0, 2018) is used directly rather than a
  `transform()`-based rebuild, since the codebase's minimum supported
  SQLite is well past that (no version-gating found for other ALTER
  TABLE features in db.py) and this mirrors `rename_table`'s direct use
  of `ALTER TABLE ... RENAME TO`.
- Assumption 2: existing-column-name collision is checked in Python
  before running SQL (via `self.columns_dict`) rather than relying on
  SQLite's own `duplicate column name` error, so the check works
  identically across SQLite versions and gives a clear `AlterError`
  message consistent with `add_column`'s existing `AlterError` usage
  for a bad `fk`/`fk_col`.
- Assumption 3: return value is `self` (Table), not `None`, following
  `add_column`/`add_foreign_key` chaining convention on `Table`, even
  though `Database.rename_table` (a different class) returns `None`.
  This is a Table method, not a Database method - task explicitly asked
  for `Table.rename_column`, unlike `rename_table` which lives on
  `Database`.
- Assumption 4: CLI `--ignore` suppresses "old column does not exist"
  and "table does not exist" errors only, not the new-name-collision
  error, matching rename-table's documented `--ignore` semantics
  ("If table does not exist, do nothing") extended to columns.
- Revision during /build: switched the missing-table case from letting
  a bare `sqlite3.OperationalError`/`AlterError` surface to an explicit
  `self.exists()` check in `Table.rename_column()` that raises

  files.
