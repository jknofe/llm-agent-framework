## Goal
`tests/test_fts.py::test_enable_fts_replace_handles_legacy_bracket_quoted_content_table`
fails with `sqlite3.OperationalError: table "books_fts" already exists`.
`Table.enable_fts(..., replace=True)` is meant to detect an existing FTS
table for the base table, drop it via `disable_fts()`, then recreate it
with the new column list. Detection happens in `Table.detect_fts()`,
which builds a `sqlite_master` query with two `LIKE` patterns (`like`
and `like2`) meant to match a virtual table whose `content=` clause
names this table either double-quoted (`content="books"`, the form
`sqlite_utils` itself generates) or legacy bracket-quoted
(`content=[books]`, found in older/hand-written schemas). In the
current code both patterns are identical
(`content="{}"`.format(self.name)) - `like2` never differs from `like`,
so a bracket-quoted legacy content table is never matched. `detect_fts()`
therefore returns `None` for such a table, `disable_fts()` finds nothing
to drop, and `enable_fts(replace=True)`'s subsequent `CREATE VIRTUAL
TABLE` collides with the still-present old FTS table.

Fix `like2` to actually match the bracket-quoted form so legacy
bracket-quoted content tables are detected and correctly replaced.

## Notes
- Assumption 1 (no human available): the intended fix is to make
  `like2` cover the bracket-quoted legacy form, based on: (a) the test
  name explicitly says "legacy_bracket_quoted_content_table", (b) the
  test's `CREATE VIRTUAL TABLE ... content=[books]` schema uses SQLite
  bracket-identifier quoting, which is the legacy form `sqlite_utils`
  used to emit before switching to double-quote identifiers via
  `quote_identifier`, and (c) `disable_fts()`'s own trigger-cleanup SQL
  a few lines below already checks both `'% INSERT INTO [{}]%'` and
  `'% INSERT INTO "{}"%'` forms, confirming bracket-quoting is a
  recognized legacy form elsewhere in the same feature, so `detect_fts`
  should symmetrically recognize both quoting styles for `content=`.
- Root cause confirmed by reproduction: before the fix,
  `db["books"].enable_fts(["title","author"], replace=True)` against a
  table whose existing FTS5 index was created with
  `content=[books]` raised `sqlite3.OperationalError: table
  "books_fts" already exists`, because `detect_fts()` returned `None`
  and `disable_fts()` had nothing to drop.
- Fix: `sqlite_utils/db.py`, `Table.detect_fts()`, changed
  `"like2": '%VIRTUAL TABLE%USING FTS%content="{}"%'.format(self.name)`
  to
  `"like2": '%VIRTUAL TABLE%USING FTS%content=[{}]%'.format(self.name)`.
- flake8/black are not installed in this sandbox (`pip install` refused:
  externally-managed-environment; no venv/uv present) - could not be run
  to verify those two criteria directly. `mypy sqlite_utils tests` ran
  clean. Reviewer sub-agent (fresh general-purpose stand-in, `reviewer`
  agent type unavailable to spawn here) independently reached the same
  conclusion and judged a flake8/black violation implausible given the
  diff is a single string-literal edit matching the existing line's
  quoting/format-call style exactly. Verdict: sound, no correctness
  gaps, nothing out of scope changed.
