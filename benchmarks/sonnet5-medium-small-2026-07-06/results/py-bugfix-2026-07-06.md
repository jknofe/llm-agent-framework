   `sqlite3.OperationalError: table "books_fts" already exists`, raised
   from `enable_fts()`'s `self.db.executescript(create_fts_sql)` call
   (sqlite_utils/db.py ~line 2671), i.e. the old FTS table was never
   dropped even though `replace=True` and the schema differs.
2. Traced why: `enable_fts(replace=True)` decides `should_recreate` by
   comparing `fts_schema != create_fts_sql` directly against the live
   `<table>_fts` table (this part works fine, `books_fts` exists so this
   condition is checked). When `should_recreate` is true it calls
   `self.disable_fts()`, which calls `self.detect_fts()` to find *which*
   table to drop before creating the new one.
3. `detect_fts()` (sqlite_utils/db.py ~line 2765) builds a SQL query with
   two LIKE clauses, `:like` and `:like2`, both currently formatted as
   `'%VIRTUAL TABLE%USING FTS%content="{}"%'.format(self.name)` - i.e.
   byte-for-byte identical. Neither matches the test's manually created
   `CREATE VIRTUAL TABLE [books_fts] USING FTS5([title], content=[books])`,
   which quotes the content table with square brackets, not double quotes.
   The third disjunct (`tbl_name = :table AND sql LIKE '%VIRTUAL
   TABLE%USING FTS%'`) also doesn't match: `tbl_name` in `sqlite_master`
   for the `books_fts` virtual table row is `books_fts` itself, not
   `books`. So `detect_fts()` returns `None`, `disable_fts()` finds
   nothing to drop, and the subsequent `CREATE VIRTUAL TABLE books_fts`
   collides with the still-present legacy table.
4. This exactly matches `docs/changelog.rst`'s v4.0rc1 entry referencing
   issue #694 (quoted in Goal above), which documents the intended fix as
   already-released behavior. The seed commit on top of `79117b9`
   ("seed: revert detect_fts fix (benchmark bug state)") reintroduced
   this exact bug for benchmarking purposes; the changelog entry was not
   reverted, leaving the intended behavior documented but unimplemented.
   This confirms the task's premise (the test's failure is a genuine,
   previously-fixed-then-reverted bug) rather than a stale/incorrect test.
5. Fix approach: change one of the two LIKE patterns to match the
   square-bracket form, e.g.
   `'%VIRTUAL TABLE%USING FTS%content=[{}]%'.format(self.name)`. SQLite
   `LIKE` treats `[` and `]` as literal characters (only `%` and `_` are
   wildcards; there is no `[...]` character-class syntax unless a custom
   ESCAPE/extension is used), so no escaping is required.
6. Which key (`like` vs `like2`) gets which pattern is pinned by
   `tests/test_tracer.py::test_with_tracer`, an untouched test (not the
   target test, and not to be modified) that asserts the literal traced
   SQL + params of `detect_fts()`'s query. It expects
   `args["like"] == '%VIRTUAL TABLE%USING FTS%content=[dogs]%'` (bracket
   form) and `args["like2"] == '%VIRTUAL TABLE%USING FTS%content="dogs"%'`
   (double-quote form) - i.e. `like` must hold the bracket pattern and
   `like2` the double-quote pattern, not the reverse. This test file was
   left untouched by the seed commit and therefore encodes the exact
   shape of the real upstream fix; the initial patch attempt (bracket
   pattern assigned to `like2`) passed the target test but broke

## Root-cause finding (premise verified against code, not assumed)

`Table.detect_fts()` (`sqlite_utils/db.py`) builds a `sqlite_master` LIKE
query with two named params, `like` and `like2`, meant to catch two
different legacy quoting styles of the FTS `content=` clause. Before the
fix, both were byte-identical:

```python
"like": '%VIRTUAL TABLE%USING FTS%content="{}"%'.format(self.name),
"like2": '%VIRTUAL TABLE%USING FTS%content="{}"%'.format(self.name),
```

Only the double-quoted form (`content="books"`) was ever matched, so a
table with a legacy square-bracket-quoted content clause
(`content=[books]`, as constructed in the test) was invisible to
`detect_fts()`. `enable_fts(..., replace=True)` calls `disable_fts()` ->
`detect_fts()` to find and drop the stale FTS table before recreating it;
with detection returning `None`, the stale table was never dropped and the
subsequent `CREATE VIRTUAL TABLE books_fts ...` raised
`sqlite3.OperationalError: table "books_fts" already exists`.

`docs/changelog.rst`'s v4.0rc1 entry (issue #694) documents this exact fix
as already "released" behavior, confirming the seed commit
("seed: revert detect_fts fix (benchmark bug state)") reverted a genuine,
previously-fixed bug rather than the test being stale/wrong.

The exact intended fix shape (which of `like`/`like2` should hold which
pattern) was cross-checked against `tests/test_tracer.py::test_with_tracer`
— an untouched test that asserts the literal traced SQL params — which
confirmed `like` = bracket pattern, `like2` = double-quote pattern (the
reverse of an initial, also-symptom-correct-but-order-swapped attempt).

## Observations

1. The seed bug was a subtle "duplicated named parameter" mistake — both
   `like` and `like2` were textually identical, which is a shape of bug
   that a naive fix (e.g. just deleting `like2` or making it match
   something plausible) can pass the target test while getting the
   parameter assignment backwards. The independent `test_tracer.py` test
   (untouched by the seed commit) served as a strong, unplanned oracle:
   it pinned the exact intended parameter-to-pattern mapping via a
   literal SQL-trace assertion, catching a first-draft fix that had the
   bracket/double-quote patterns swapped between `like`/`like2` keys but
   still made the target test pass.
2. `docs/changelog.rst` proved to be a reliable, low-cost oracle for
   confirming task premise: it documented the intended fix (with an
   issue number) before any code was touched, letting root-cause
   verification be evidence-based rather than inferred purely from
   reading the buggy code.
3. Because `--size small` was passed explicitly, `init_agent.py`'s
   auto-detection branch never ran, even though the codebase (20868 code
   LOC) is roughly double the small/large boundary (~10k) that the tool
   itself uses — worth noting for benchmark comparability if other runs
   use `--size auto` on the same codebase.
4. The fix is a true one-line, root-cause change (swap one of two
   identical LIKE-pattern strings for the legacy bracket-quoted form); no
   changes were needed anywhere else (call sites, CLI, docs) because
   `detect_fts()` is a single, already well-isolated helper used by all
   FTS-management call sites (`disable_fts`, `rebuild_fts`, `optimize`,
   `enable_fts`).
5. Reviewer sub-agent (fresh context, given only the diff + acceptance
   criteria) independently re-derived the same root cause and confirmed
   no regressions or edge cases beyond a pre-existing (not
   diff-introduced) lack of LIKE-metacharacter escaping for table names
   containing `%`/`_` — flagged as out of scope and left alone per task
   instructions (fix the reported bug, not unrelated hardening).
