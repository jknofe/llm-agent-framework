## Observations

1. Root cause: `Table.detect_fts()` builds a SQL `LIKE`-based sniffing query
   with two placeholders, `:like` and `:like2`, meant to catch both the
   legacy bracket-quoted content-table syntax (`content=[books]`, produced by
   old SQLite/tools) and the modern double-quoted syntax (`content="books"`).
   Both placeholders were bound to the *same* double-quoted pattern, so a
   table whose FTS shadow was declared with bracket quoting (as older schemas
   do) was never detected. `enable_fts(replace=True)` then skipped the
   `disable_fts()` cleanup path's actual drop (detect_fts returned None, so
   `drop()` never ran) and the subsequent `CREATE VIRTUAL TABLE` collided
   with the still-existing `books_fts` table, raising
   `sqlite3.OperationalError: table "books_fts" already exists`.

2. The correct expected values for the two patterns were independently
   pinned in `tests/test_tracer.py` (line 67-68), which asserts `like` is the
   bracket-quoted variant and `like2` is the double-quoted variant. This
   made the fix unambiguous — the tracer test would have caught a
   surface-level typo fix that swapped the wrong placeholder or used the
   same string for both.

3. The fix is a one-line, minimally-scoped change confined to a `LIKE`
   pattern string inside `detect_fts()`. It does not touch table rewriting,
   column rename/drop, or add any new public method, so it has no bearing on
   the project's rule that new public methods must avoid `Table.transform()`
   and must use `ALTER TABLE ... RENAME/DROP COLUMN` directly. Full suite:
   1080 passed, 16 skipped, 0 failed after the fix (previously 1 failure).
