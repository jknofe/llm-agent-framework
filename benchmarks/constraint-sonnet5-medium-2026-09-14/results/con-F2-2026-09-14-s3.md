## Observations

1. Read both `AGENTS.md` and `.ai/notes.md` before touching code, as the
   protocol requires. `AGENTS.md`'s generated project-context section
   directly dictated the implementation: it explicitly says column
   renames/drops must use `ALTER TABLE ... RENAME COLUMN` / `ALTER TABLE
   ... DROP COLUMN` directly, and that new public methods must never call
   `Table.transform()`. Without that rule I would have defaulted to
   reusing the existing `transform(drop=...)` path (there's already a
   `transform_drop_columns` doc anchor for exactly that), which is the
   wrong pattern for a new single-column primitive.

2. `.ai/notes.md` had a prior entry for `Table.rename_column()` recording
   that SQLite's own `ALTER TABLE RENAME COLUMN` already raises
   `sqlite3.OperationalError` and leaves the table unchanged on a missing
   column, so no Python-side pre-check is needed. I used that same
   reasoning directly for `drop_column` (skipped writing a redundant
   "does column exist" check) and verified the same guarantee holds for
   `DROP COLUMN` via the new tests (`test_drop_column` in both
   `test_create.py` and `test_cli.py` assert `columns_dict` and `rows`
   are unchanged after the raised error).

3. Undocumented-in-AGENTS.md pitfall discovered by grepping first: the
   CLI reference page (`docs/cli-reference.rst`) is cog-generated from a
   `commands.keys()` walk plus a hand-maintained `refs` dict mapping each
   command name to its narrative-doc anchor. Adding the CLI command alone
   would have made `cog --check` pass (cog doesn't fail on missing
   dict entries, it just omits the "See ..." backlink), so this needed
   deliberate grep-and-cross-check against how `rename-column`'s entry
   was wired, not something the test suite would catch by itself.
