## Root cause

`Table.detect_fts()` (sqlite_utils/db.py) builds a SQL query with two LIKE
patterns, `:like` and `:like2`, meant to catch two different historical
quoting styles SQLite uses for the FTS5 `content=` clause: legacy
bracket-quoting (`content=[books]`) and modern double-quoting
(`content="books"`). Both patterns had been set to the *same* double-quote
string, so a legacy bracket-quoted content table (e.g. one created by an
older sqlite-utils version, or manually) was never matched by `detect_fts()`.

This broke `enable_fts(..., replace=True)`: it correctly decided the existing
FTS table needed to be recreated (`should_recreate = True`, since the stored
schema text differs byte-for-byte from the freshly rendered `CREATE VIRTUAL
TABLE` SQL), called `disable_fts()`, but `disable_fts()` calls `detect_fts()`
to find the table to drop, got `None` back, and silently skipped the drop.
The subsequent `CREATE VIRTUAL TABLE "books_fts" ...` then failed with
`sqlite3.OperationalError: table "books_fts" already exists`.

`tests/test_tracer.py::test_with_tracer` independently pins the exact SQL and
bound parameters `detect_fts()` is expected to issue, with `like` bound to
the bracket-quoted pattern and `like2` bound to the quoted pattern -- this
confirmed the correct/original assignment of the two patterns (not just "any
two different patterns") and is why the fix restores `like` to the
bracket-quoted form rather than deduplicating the other way.

## Fix

Changed the `"like"` pattern in `detect_fts()` from a duplicate of `"like2"`
back to the bracket-quoted legacy form: `content=[{name}]` instead of
`content="{name}"`. `"like2"` (double-quote form) is unchanged. No other
files touched. No use of `Table.transform()` was introduced or needed --
`disable_fts()` already removes the old FTS table via plain `DROP TABLE`
(through `Table.drop()`), consistent with the project rule that new/changed
public-method behavior must not go through `transform()`.

## Observations

1. This was a one-character-class typo bug disguised as two independent-looking
   dict entries (`like` / `like2`) -- easy to miss on a quick read because both
   lines are visually similar and syntactically valid; only tracing actual
   `sqlite_master` matching behavior (or the pinned `test_tracer.py` expectations)
   reveals the swap.
2. `tests/test_tracer.py::test_with_tracer` acted as a second, independent oracle
   for the correct fix: it asserts the literal SQL and bound parameter dict passed
   to `db.execute()`, which pinned not just "two different LIKE patterns" but their
   exact assignment to `like` vs `like2`. My first fix attempt (swapping which
   variable got which pattern, in the opposite order) passed the target test but
   broke `test_with_tracer` -- a reminder to run the *whole* suite before declaring
   victory, since a locally-plausible fix can satisfy the named test while violating
   an unrelated pinned-behavior test elsewhere.
3. The fix required no `Table.transform()` usage and none of the surrounding code
   (`disable_fts`, `enable_fts`, trigger cleanup) needed to change -- the bug was
   isolated entirely to the detection query, so the "column renames/drops must use
   ALTER TABLE directly" guidance for this project was not implicated by this
   particular task, but is worth keeping in mind for any future FTS/schema work
   in this file since `enable_fts`/`disable_fts` sit right next to schema-mutating
   code paths.
