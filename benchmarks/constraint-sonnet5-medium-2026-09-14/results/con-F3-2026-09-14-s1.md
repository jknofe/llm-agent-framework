## Root cause

`Table.detect_fts()` in `sqlite_utils/db.py` builds two SQL `LIKE` patterns,
`like` and `like2`, meant to match a table's FTS shadow table in
`sqlite_master` under either of the two ways SQLite schemas quote the
`content=` clause: double-quoted (`content="table"`, produced by current
`enable_fts()`) or legacy bracket-quoted (`content=[table]`, as produced by
older code/tooling, and by the test's manually-executed `CREATE VIRTUAL
TABLE ... content=[books]`). Before the fix, both dict entries held the
*same* double-quote pattern, so bracket-quoted legacy FTS tables were never
matched by `detect_fts()`.

That fed into `enable_fts(replace=True)`: it correctly decided the existing
`books_fts` schema differed from the new one and set `should_recreate =
True`, then called `self.disable_fts()`. `disable_fts()` calls
`detect_fts()` to find the table to drop, got `None` back (bug), so the drop
was silently skipped. `enable_fts()` then ran `CREATE VIRTUAL TABLE
"books_fts" ...` against a database where `books_fts` still existed, raising
`sqlite3.OperationalError: table "books_fts" already exists`.

## Fix

Restored the `like` pattern to the bracket-quoted form
(`content=[{}]`.format(self.name)) so the two patterns cover both quoting
styles, matching the exact pairing (`like` = bracket form, `like2` =
double-quote form) that `tests/test_tracer.py::test_with_tracer` asserts on
the literal query-args dict.
