## Observations

1. **Read both `AGENTS.md` and `.ai/notes.md`; used content from both.** `AGENTS.md`'s generated project-context section directly shaped the implementation: it states "Column renames and drops use `ALTER TABLE ... RENAME COLUMN` ... directly, even though older code in this repo does it the other way" and "`Table.transform()` rewrites the whole table ... New public methods must never call it." Without that, the more "discoverable" path from reading `db.py` would have been to implement `rename_column` via `transform(rename={...})`, since that machinery already exists and is what `sqlite-utils transform --rename` uses under the hood. The note steered me to hand-write the direct `ALTER TABLE ... RENAME COLUMN` SQL instead (mirroring `rename_table`'s direct `ALTER TABLE ... RENAME TO` pattern), matching the intended new-code style. `.ai/notes.md` had one prior entry (an FTS bug fix) that wasn't relevant to this task; I appended a new entry recording the changelog-omission assumption and the "raise before executing" design choice, then committed `.ai` per protocol step 4.

2. **The "raise and leave unchanged" requirement was satisfied by ordering, not by a transaction/rollback.** Rather than trying the `ALTER TABLE RENAME COLUMN` and catching a possible SQLite-version-dependent `OperationalError` on collision, `rename_column()` checks `column not in self.columns_dict` and `new_column in self.columns_dict` up front and raises `AlterError` *before* calling `self.db.execute(...)`. This makes "unchanged on collision" true by construction regardless of what a given SQLite build does with `RENAME COLUMN` onto an existing name, and gives a consistent exception type (`AlterError`) across Python versions/SQLite builds, consistent with how `add_column`/`add_foreign_key` validate before executing.

3. **One doc surface is enforced by a test, one cog block had to be hand-updated and regenerated, and one doc file was deliberately skipped.** `tests/test_docs.py::test_commands_are_documented` parses `docs/cli.rst` for `sqlite-utils <command>` lines and fails if a CLI command isn't documented there — this caught the missing doc immediately (first full-suite run had exactly 1 failure: `test_commands_are_documented[rename-column]`). Fixing it required adding a "Renaming a column" section to `docs/cli.rst`, then also updating the `refs` dict inside `docs/cli-reference.rst`'s embedded `cog` script and running `cog -r docs/cli-reference.rst` to regenerate its `--help`-derived body (a plain text edit there would have been immediately stale/wrong, and `cog --check` would have failed). I deliberately did *not* add a `docs/changelog.rst` entry: the top section there is a dated version heading that may already be released, entries elsewhere carry `:issue:` numbers I have none for, and `AGENTS.md`'s stated gate is only `pytest` + `cog --check README.md docs/*.rst`, neither of which touches changelog content — recorded as an assumption in `.ai/notes.md` rather than guessed silently.
