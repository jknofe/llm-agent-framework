## Root cause

`Table.detect_fts()` (sqlite_utils/db.py) builds two SQL LIKE patterns to find
a table's associated FTS shadow table by inspecting `sqlite_master.sql`: one
pattern for the modern double-quoted form (`content="table"`) and one for the
legacy bracket-quoted form (`content=[table]`), historically produced by
hand-written schemas or older sqlite-utils versions. Both `like` and `like2`
were set to the *same* double-quote pattern, so the bracket-quoted legacy
form was never matched.

Effect on the failing test: it creates an FTS5 table manually using
`content=[books]` (legacy bracket quoting), then calls
`enable_fts(["title","author"], replace=True)`. `enable_fts()` compares the
existing schema against the freshly generated one, decides they differ
(different columns), and calls `disable_fts()`. `disable_fts()` calls
`detect_fts()` to find the shadow table to drop -- but with both patterns
being the double-quote pattern, `detect_fts()` failed to match the
bracket-quoted `books_fts` table, so it was never found and never dropped.
`enable_fts()` then executed `CREATE VIRTUAL TABLE "books_fts" ...`, which hit
`sqlite3.OperationalError: table "books_fts" already exists`.

## Fix

Restored `like` to the bracket-quote pattern (`content=[{}]`) while keeping
`like2` as the double-quote pattern (`content="{}"`) -- this exact
`like`/`like2` order is also pinned by
`tests/test_tracer.py::test_with_tracer`, which asserts the literal SQL args
passed to `db.execute()` during `search()`'s underlying `detect_fts()` call
(this surfaced as a second, unrelated-looking failure the first time the two
patterns were naively swapped/deduplicated the other way -- caught by running
the full suite, not just the named test).
