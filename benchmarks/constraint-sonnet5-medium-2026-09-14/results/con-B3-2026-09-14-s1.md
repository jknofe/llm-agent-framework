## Observations

1. **Root cause**: `Table.detect_fts()` builds a `sqlite_master` LIKE query with two
   supposedly-different patterns, `:like` and `:like2`, meant to catch both the modern
   double-quoted `content="books"` form and a legacy bracket-quoted `content=[books]`
   form emitted by older SQLite tooling. Both keys were accidentally set to the exact
   same double-quoted pattern, so tables created with `content=[books]` were never
   detected. `enable_fts(..., replace=True)` relies on `detect_fts()` inside
   `disable_fts()` to find and drop the pre-existing FTS shadow table before recreating
   it; when detection silently failed, the old `books_fts` virtual table was left in
   place and the subsequent `CREATE VIRTUAL TABLE "books_fts" ...` collided with it,
   raising `sqlite3.OperationalError: table "books_fts" already exists`.

2. **Fix and its shape were constrained by an existing test**: `tests/test_tracer.py::
   test_with_tracer` already asserted the exact SQL/params tuple `detect_fts()` should
   produce, including which of `like`/`like2` holds the bracket pattern vs the
   double-quote pattern (`like` = bracket, `like2` = double-quote). That test was
   failing on the unmodified repo too (i.e., it was already red before my change,
   not a regression I introduced), so this task actually had two co-located,
   related failures sharing one root cause. My first attempt fixed detection
   correctness but put the bracket pattern in `like2`/quote pattern in `like` (the
   "obvious" order matching original code position), which passed the FTS test but
   failed the tracer test on argument order; swapping the two literals to match the
   tracer test's expectations fixed both simultaneously. Lesson: always run the full
   suite, not just the named failing test, before declaring done, since a narrow fix
   can satisfy the named test while missing an already-present sibling assertion on
   exact call shape.

3. **No `Table.transform()` involvement needed**: this bug lived entirely in a
   read-only detection query (`detect_fts`) built from a static SQL template; no new
   public method was added and no column rename/drop was required, so the
   transform-avoidance rule for this project didn't come into play here. Noted for
   awareness only, in case a future fix in this area is tempted to reach for
   `ALTER TABLE` rewrites — a straight two-line LIKE-pattern correction was sufficient.
