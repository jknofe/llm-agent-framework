## Observations

1. **Existing `AlterError` convention reused, not a new exception type.** `rename_table` (Database-level) only wraps `sqlite3.OperationalError` because it does no pre-validation. For `rename_column` the task explicitly requires "raise and leave the table unchanged" on a name collision, so validation had to happen *before* touching SQLite. The codebase already has this exact pattern in `add_foreign_key`/`add_foreign_keys` (`AlterError("No such table: ...")`, `AlterError("No such column: ...")`), so `rename_column` raises `AlterError` for all three failure modes (missing table, missing source column, colliding target column) instead of letting SQLite raise `OperationalError`. This keeps the CLI's `except AlterError` catch consistent with `add-foreign-key`'s CLI command rather than `rename-table`'s.

2. **`ALTER TABLE ... RENAME COLUMN` is available and used directly (no `transform()` fallback).** The table already had a `transform(rename={...})` method that can rename columns via a full table rebuild, but that's overkill and not what "mirror `rename_table()`" asked for — `rename_table()` is a single `ALTER TABLE RENAME TO`. `ALTER TABLE t RENAME COLUMN old TO new` has been supported since SQLite 3.25 (2018) and Python 3.12's bundled SQLite is far newer, so no version-gating was added, matching the simplicity of `rename_table`.

3. **Doc regeneration required a docker round-trip since `docs/cli-reference.rst` is `cog`-generated.** `docs/cli-reference.rst` embeds live `--help` output via `cog`. Editing only the `refs` dict manually would have left the actual rendered `Usage:`/`Options:` block missing. Ran `cog -r README.md docs/*.rst` inside the same `python:3.12` container (with `cogapp` installed) to regenerate it in place, then verified with `cog --check` that all doc files are consistent with the code. `docs/cli.rst` and `docs/python-api.rst` were edited by hand (prose docs, not cog-templated) mirroring the existing "Renaming a table" sections.
