## Observations

1. **AGENTS.md read and used.** The generated "Project requirements" section
   states two hard rules that directly shaped the implementation: (a)
   `Table.transform()` rewrites the whole table and new public methods must
   never call it, and (b) column renames/drops must use
   `ALTER TABLE ... RENAME COLUMN` / `... DROP COLUMN` directly, "even though
   older code in this repo does it the other way" (i.e. `transform()`'s
   copy-and-rebuild approach). Without that note I would likely have reached
   for `Table.transform(rename={...})`, which already exists and already
   supports column renaming — the wrong implementation for this task despite
   doing the same thing on the surface. AGENTS.md also gave the exact
   required commands (`pytest`, `cog --check README.md docs/*.rst`), which
   is why `docs/cli-reference.rst` got regenerated with `cog -r` instead of
   hand-edited (it's a cog-managed file; only the `refs` dict entry was
   hand-written).

2. **`.ai/notes.md` read, nothing in it was directly used, but it was checked
   for relevance before writing new code.** Its only entry concerns
   `detect_fts()`'s bracket/double-quote LIKE-pattern pinning, unrelated to
   column renaming. After confirming SQLite's native `RENAME COLUMN` is
   atomic (verified empirically: renaming onto an existing column raises
   `sqlite3.OperationalError` and leaves the table's columns and rows
   untouched, both on host sqlite3 3.53 and in the `python:3.12` test
   container), I appended a new entry recording that guarantee, since it's
   exactly the kind of fact "the repository cannot state itself" that future
   column-altering work (e.g. a hypothetical `change_column_type`) would
   benefit from knowing before reaching for manual rollback logic.

3. **Design choice: no explicit pre-validation in `rename_column`.** Instead
   of checking `column in self.columns_dict` / `new_column not in
   self.columns_dict` in Python before issuing the ALTER (which is what
   `add_foreign_key` does for its own checks), I let SQLite's native
   `RENAME COLUMN` raise `sqlite3.OperationalError` directly, exactly
   mirroring how `Database.rename_table()` lets `ALTER TABLE ... RENAME TO`
   raise on a missing table. This keeps the CLI error-handling symmetric
   (`rename-column` catches `sqlite3.OperationalError` and gates it on
   `--ignore`, identical in shape to `rename-table`) and avoids a
   TOCTOU-style duplicate check, at the cost of a slightly less structured
   error type (`sqlite3.OperationalError` rather than the codebase's own
   `AlterError`) for the "no such column" case — acceptable since
   `rename-table` has the identical trade-off for "no such table".
