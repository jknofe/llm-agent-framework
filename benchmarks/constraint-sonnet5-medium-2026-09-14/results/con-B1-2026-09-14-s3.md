## Observations

1. **Implementation mirrors `rename_column`, not `transform(drop=...)`.** The codebase already had a column-drop *capability* via `Table.transform(drop=[...])`, which rebuilds the whole table (create-new / copy-rows / drop-old / rename). Rather than wrap that heavier machinery, `drop_column` was implemented as a single `ALTER TABLE "table" DROP COLUMN "col"` statement, matching the existing `rename_column` method's shape (native `ALTER TABLE ... RENAME COLUMN`) and requiring SQLite 3.35.0+ (the `python:3.12` image ships SQLite 3.46.1, well past that floor). No version-gating code exists elsewhere in `db.py` for `rename_column`'s 3.25.0 requirement either, so none was added here for consistency.

2. **The "must raise and leave the table unchanged" requirement is satisfied by an existence check *before* any SQL runs**, not by try/except-and-rollback: `drop_column` looks up `column not in self.columns_dict` and raises `AlterError` immediately, so the `ALTER TABLE` statement never executes on a missing column. This is exactly how `rename_column` guards against a missing source column, and it's simpler/cheaper than wrapping the ALTER in a transaction and catching `sqlite3.OperationalError`.

3. **`tests/test_docs.py::test_commands_are_documented` is a hard gate that would have failed silently otherwise.** It parametrizes over every registered Click command and asserts a `sqlite-utils <command>` invocation string appears somewhere in `docs/cli.rst` or `docs/plugins.rst`. Without adding the narrative "Dropping a column" section (with a `sqlite-utils drop-column mydb.db mytable columntodrop` example) to `docs/cli.rst`, the new CLI command would have made this test fail. Separately, `docs/cli-reference.rst` is cog-generated from live `--help` output (`Justfile`'s `cog` recipe) — running `cogapp` after adding the ref-anchor mapping (`"drop-column": "cli_dropping_columns"`) regenerated that file's `drop-column` block automatically; hand-editing it would have drifted on the next `cog -r` run.
