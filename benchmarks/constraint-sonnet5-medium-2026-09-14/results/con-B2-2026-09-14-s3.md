## Observations

1. **The codebase already had a "correct" drop-column primitive that isn't a raw `ALTER TABLE ... DROP COLUMN`.** `Table.transform(drop=[...])` (used internally by `extract()` and elsewhere) rebuilds the table via create-copy-swap, which handles SQLite versions without native `DROP COLUMN` support and correctly carries over indexes, foreign keys, `NOT NULL`, and defaults for the surviving columns. Implementing `drop_column` as a raw ALTER statement would have been simpler to write but a strictly worse, less-portable implementation; recognizing and reusing the existing `transform()` path was the highest-leverage design decision in this task.

2. **`transform(drop=...)` alone does not satisfy the "must raise on missing column" requirement** — it silently ignores unknown names in the `drop` set (the drop logic only removes matching entries from the existing column list, per `transform_sql()`'s `if name in drop: continue` loop). This meant an explicit `if column not in self.columns_dict: raise AlterError(...)` guard was mandatory, not optional polish, for the task's stated invariant ("leave the table unchanged" on error) to actually hold.

3. **This is the second of two column-level ALTER operations added back-to-back in this codebase** (`rename_column` per the changelog's `4.0rc1` entry, now `drop_column`), and both share the exact same seam: CLI command catches `(sqlite3.OperationalError, AlterError)`, wraps in `click.ClickException` unless `--ignore`, and the Python API raises `AlterError` directly. Mirroring `rename_column`'s structure (rather than `add_column`'s, which has more surface area for FK handling) produced a smaller, more consistent diff than following the letter of "mirror add-column/add_column" would have, since `rename_column` is the closer structural analog for a single-column-name-only mutation.
