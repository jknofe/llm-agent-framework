## Root cause

`Table.detect_fts()` (sqlite_utils/db.py ~line 2765) builds a `sqlite_master`
query with two LIKE patterns meant to catch both quoting styles SQLite uses
for the FTS `content=` clause: the legacy bracket-quoted form
`content=[books]` and the current double-quoted form `content="books"`. The
bug seed set both `like` and `like2` to the same double-quoted pattern, so a
`content=[books]`-style FTS table (as produced by older sqlite-utils
versions, or hand-written SQL, per the test's docstring/name) was invisible
to `detect_fts()`. `disable_fts()` calls `detect_fts()` to find the table to
drop before recreating it; with detection failing, `enable_fts(..., replace=True)`
skipped the drop and then tried to `CREATE VIRTUAL TABLE books_fts`, which
already existed, raising `sqlite3.OperationalError: table "books_fts" already
exists`.

## Fix

Restored `like` to the bracket-quoted pattern (`content=[{}]`), keeping
`like2` as the double-quoted pattern. Confirmed the intended assignment (not
just any two-distinct-patterns fix) against `tests/test_tracer.py::test_with_tracer`,
which hardcodes the full traced SQL and params dict and pins `like` to the
bracket pattern and `like2` to the quoted pattern - an initial attempt that
put the bracket pattern into `like2` instead passed the target FTS test but
broke `test_with_tracer`, which is a real pre-existing test, not a
benchmark-specific artifact.
