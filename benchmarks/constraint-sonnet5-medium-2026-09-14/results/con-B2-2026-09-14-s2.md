## Observations

1. **`rename_table` is a `Database`-level method, but `rename_column` had to be a `Table`-level method.** The existing pattern (`db.rename_table(name, new_name)`) lives on `Database`, while the task explicitly asked for `Table.rename_column(old, new)`. Mirroring "the pattern" therefore meant matching the *style* (a single `ALTER TABLE ...` statement, thin CLI wrapper, `--ignore` flag with identical semantics) rather than the literal class placement. Placed the new method next to `add_column` in the `Table` class, since both are column-level single-statement ALTER operations.

2. **SQLite's native duplicate-column error was usable but not chosen.** Experimentally verified (via a throwaway `python:3.12` container) that `ALTER TABLE ... RENAME COLUMN a TO b` where `b` already exists raises `sqlite3.OperationalError: ... duplicate column name: b` and leaves the table's columns unchanged - so the bare native statement would have technically satisfied "must raise and leave the table unchanged" with zero extra code. Chose instead to add an explicit pre-check raising the existing `AlterError` exception (the same exception `add_column` uses for its own validation failures), for a clearer and more deterministic error message/type, at the cost of one extra `columns_dict` lookup before the ALTER statement.

3. **A quoting-related error-message trap was caught by writing a real assertion instead of a guessed one.** Because `rename_column` uses `quote_identifier()` on the column name (matching `rename_table`'s use of it), SQLite's own "no such column" error message ends up with doubled quotes (`no such column: ""missing""`) rather than the unquoted `no such column: "missing"` one would get testing the bare SQL directly. Caught this only by actually invoking the CLI path in a container and reading `repr(result.output)` rather than trusting the raw-SQL experiment from observation 2 - a good reminder that identifier quoting changes error-message shape, not just query semantics.
