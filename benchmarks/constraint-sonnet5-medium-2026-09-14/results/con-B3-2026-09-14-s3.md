## Observations

1. **This task built directly on prior sessions' work in the same repo**: the
   working tree already had T1 (`detect_fts` fix) and T2 (`rename-column`)
   committed. T2's `rename_column` implementation (pre-validate with
   `self.exists()` / `name in self.columns_dict`, raise `AlterError`, execute
   a single native `ALTER TABLE ... RENAME COLUMN` statement) turned out to be
   a closer structural match for this task's "raise and leave unchanged"
   requirement than the nominally-requested mirror target (`add_column`,
   which has no failure-on-missing-thing case to mirror). Reusing the T2
   pattern kept the new `drop_column` consistent with a convention already
   established in this exact codebase rather than introducing a second way
   of doing pre-validated alters.

2. **Single native SQL statement was correct and simplest**: `ALTER TABLE
   ... DROP COLUMN` has been supported by SQLite since 3.35.0 (2021); the
   `python:3.12` Docker image used for the test command bundles SQLite 3.46.1,
   so no fallback to the heavier `Table.transform(drop=[name])` full-table-rebuild
   path (used pre-3.35, or when the column being dropped participates in an
   index, is part of the primary key, or has a `CHECK`/generated-column
   dependency that `DROP COLUMN` itself refuses) was needed, and no version
   gating was added to `drop_column` itself.

3. **Cog-generated doc stayed in sync mechanically, not by hand-editing**:
   `docs/cli-reference.rst` embeds a Python cog block that drives
   `--help` output through a `refs` dict keyed by CLI command name. Adding
   `"drop-column": "cli_dropping_columns"` to that dict and re-running
   `python -m cogapp -r docs/cli-reference.rst` inside the same Docker
   container used for the test suite (rather than typing the `Options:` block
   by hand) guarantees the reference page can never drift from the actual
   `drop-column --help` text - the same mechanism the prior T2 session used
   for `rename-column`.
